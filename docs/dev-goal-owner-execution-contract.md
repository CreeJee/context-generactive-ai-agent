## Plan v13 approved provenance and completion-evidence contract

Central-owner registration is execution authorization, not proof that a Goal succeeded. Only artifacts produced through the owner-managed generation path may be adopted automatically after provenance, integrity and execution-contract validation. External/manual artifact import is outside this implementation scope. Existing SDK-only pins must not acquire current native code through inferred backfill or implicit replacement.

During execution, retain durable references from each run to its Goal/Plan versions and artifact generation, together with actual changes, verification results, errors, cancellation and unresolved effects. Explicit generation transitions require their own evidence. Failed or cancelled runs retain evidence; completion is not the first persistence point.

At Goal completion, connect each success criterion to the applicable Plan steps, actual runs and verification evidence, and connect those runs to their registered execution provenance. Registration evidence must never substitute for passed verification. Prefer the existing central DB and evidence tree; do not duplicate credentials or entire code bundles in the tree. Artifact identity/hash supports provenance, but reproducing code requires retaining the actual artifact. Deleting the artifact must not be described as preserving reproducibility through its hash alone.

This section records the approved contract, not implementation completion. P03B3 implements registration and execution references; P04 implements and verifies criterion-linked completion records and documents retention/rollback limits. The release reader's safe rejection and pre-upgrade-backup rollback policy below remain mandatory; no automatic legacy provenance backfill is authorized.

A tool-side effect may complete between worker death and owner acknowledgment. Persist a call intent/idempotency key, deny automatic retry if outcome is uncertain, and keep existing permission decisions rather than converting uncertainty into approval.
- The minimum experiment is one real `AgentChat` turn in the fake-provider/temporary-DB harness with no external tool effects, but with **separate owner and executor processes**. Until the transaction and versioned tool surface above exists, the current whole `AgentChat` cannot be used as that worker. The existing baseline proves only completed transcript/run persistence after reopening the same owner DB, same-process SSE replay, wrong-session replay denial, and fail-closed running-run recovery (`agent-chat-goal-boundary.test.ts`, `runs.test.ts`).

## P03B2 first partial probe (not a completed boundary)

`packages/memory-agent/tests/agent-chat-worker-model.test.ts` executes the **fake model responder** in a child process without DB access, consumes its answer through a real `AgentChat` turn in the owner runtime, terminates that child, reopens the same owner DB, and checks one run/user/assistant record remains. Its child process is not a full Goal worker: `AgentChat` orchestration, tool and workflow code, run claim and SSE still execute in the owner process. This proves only that moving a model computation away does not force a second DB owner for a completed tool-free turn. A second test has the **test-only model responder** exit before responding; the owner records a failed bound run, and after reopening the DB the same or a new run ID cannot silently re-execute it. It does **not** prove the immutable Goal code boundary, production provider/worker execution, owner-restart SSE cursor replay, tool-effect fencing, or an authorized recovery path after an uncertain outcome. A narrow production `AgentChat.handle` check now rejects a pre-existing run ID belonging to another session before writing a user node (`agent-chat-goal-boundary.test.ts`); the prior `createOrResume` global-ID conflict was reproduced first. This read-then-check guard is **not atomic** across competing processes and does not bind a Goal, so it does not replace owner admission. Production worker routing is unchanged; additive revisions, identity, binding, receipt and binding-integrity migrations now exist. P03B2 remains open and P03B3 must not start.

## Minimal RPC and persistence invariants to validate in P03B2

1. **Admission:** the current HTTP chat route checks the request origin and reads a client-provided session ID; it does **not** authenticate a user (`apps/agent/app/routes/api/chat.tsx`). The current server is loopback-only. The stored Goal currently has a mutable `version`, but **no stable Goal ID** (`src/workflow/workflow.ts`); use a separately assigned durable `goal_instance_id` for a Goal spanning Plan revisions, and treat the version as a fencing revision, not identity. Existing Goals need an explicit compatible backfill/mapping before worker routing; never derive an identity solely from a statement or version. Before admitting a worker run, the central owner must resolve and validate that session and its Goal from its own stored state, check any required session lease/permission rule, and bind `(session_id, goal_instance_id, goal_version, run_id, worker_generation, owner_epoch, protocol_version)` in central persistent state _before_ dispatch. One active run per session and one immutable binding per run ID; repeat admission returns the same accepted run or explicit conflict, never a second execution. A client-supplied Goal, URL, session ID or worker PID cannot authorize access to another session or worker; a worker capability is internal and must be scoped to that central binding. Adding network/user authentication would be a separate design, not an existing protection.
2. **Execution:** the pinned worker gets a narrowly scoped command and opaque capability bound to that tuple. No path to `memoryAgentLayer(storageRoot)`, SQLite, vector writer, embedding/keychain/OAuth callback owner or central mutable process-global state. The present `AgentChat.make` captures `sqlite`, `Nodes`, tools, provider, workflows and live runs in one closure, so simply moving it wholesale fails this rule. Define an execution service interface and owner-only effects at each call site before starting a real turn across IPC; a model-only worker is insufficient when tools/workflow logic are Goal-sensitive.
3. **Writes and events:** owner validates session/run binding and fencing epoch on each result, tool decision and event. A `(run_id, sequence)` unique key and monotonically increasing cursor make retries idempotent; commit before publishing SSE. Replay reads committed events after cursor and then subscribes to new events without a gap. A completed run's transcript/nodes and terminal marker must be queryable after owner restart. Never promise exact replay from the current in-memory SSE adapter or backfill unseen historical frames from chat transcript.
4. **Worker death/cancellation:** atomically mark unfinished execution `failed` or `uncertain`, keep committed evidence, and reject stale worker results. No automatic re-execution after an external tool may have run: retain call ID, approval and last acknowledged result, show uncertain outcome for manual confirmation. Cancellation and terminal transitions must be idempotent and fenced. Pending approvals must never turn into implicit approval; lost continuation is failed/cancelled until restored by a proved compatible worker.
5. **Versioning:** pin old Goal code and its protocol version until Goal completion or explicit, verified migration; new Goals may select new code. Owner should support overlapping RPC versions only as long as active Goals need them, and reject unknown payload versions without mutating DB. An owner failure must not start another owner against the same storage while old callbacks/workers still write.

## P03B2 Goal and Plan identity contract (approved direction; partial implementation)

`Workflows.updateGoal` replaces the current Goal and increments its mutable version; `updatePlan` replaces the current Plan. The additive `workflow_state_revisions` migration now captures the **currently available** legacy state (marked `legacy_current`) and each subsequent full-state save in the same central DB transaction as `session_workflows`. It preserves past Goal, Plan and evidence snapshots after revisions; an immutability trigger rejects edits. It cannot reconstruct prior legacy versions, bind old runs to Goals or make an executor safe to route. A second additive migration records a stable random `goal_instance_id` for the **first new Goal in a new session** and attaches it to subsequent snapshots. Existing Goals deliberately remain unbound (`NULL`), rather than guessing identity from text or versions. No new worker routing is enabled.

The approved direction distinguishes **changing the Plan's method** (Plan version only) from **adding or changing the result/success criteria** (new Goal version under the same Goal ID and a corresponding Plan revision). An independently judged new objective must be an explicit new Goal ID; a worker generation is a separate, pinned execution identity. Historical evidence is not silently promoted to satisfy a new criterion. The new identity is not derived from text or a version. Explicitly starting a separate session creates a separate Goal ID, but a same-session, separately authorized new-Goal transition is not yet implemented; the current identity table has one current Goal per session, so never relabel existing run bindings to simulate one. The owner-side `workflow_run_bindings` table and `workflowRunBindings.bind()` now preserve a manually reserved run's immutable Goal/Plan revision and reject stale revision, duplicate run ID and unresolved earlier run. A test reserves one before a real `AgentChat` turn and reopens the DB. `AgentChat.handle()` now rejects another session's use of a pre-bound run ID before adding a user node or starting the SDK run. `handle()` also rejects an unstarted bound run after its Goal/Plan revision changes, before adding the user node. A manually bound unresolved run now blocks a different unbound run ID before writing a node, and a bound `failed` run ID cannot start the model again. This is a fail-closed _partial guard_, not a solution for resolving uncertain outcomes: a reservation abandoned before `chat_runs` creation can still block subsequent turns indefinitely until an explicitly authorized, evidenced recovery path exists. This is **not** automatic admission: `handle()` does not create the binding, these reads are not an atomic admission with SDK run/node creation, and the binding API alone does not authorize a session. Until request authorization, automatic run admission and explicit new-Goal transition are persisted and tested, fail closed for Goal-worker routing; do not infer old `chat_runs` membership, and label ambiguous old runs legacy/unbound. Current tools do not yet enforce method-versus-outcome classification.

An additive `workflow_run_events` table now accepts centrally committed output receipts for a manually bound run with idempotent event keys, session-scoped cursor replay and rejection of contradictory retries. A real `AgentChat` model turn, including a test-only child-process model response, writes its output chunks before handing them to the SSE encoder; reopening the owner DB retains those receipts. This is **not** HTTP SSE replay after an owner restart: the SDK still uses `memoryStream`, and no worker authorization, execution fencing, tool-result journal or automatic run admission is enabled. A separate cross-session replay regression exposed an SDK/request mismatch: an offset can select a different run than the validated `?runId`. `AgentChat.hydrate` now requires the validated query run, `X-Run-Id` (if present), and `Last-Event-ID`/query offset to identify the same run before invoking the SDK; this protects the current in-memory path but is not an owner-restart solution. The installed SDK's `StreamDurability` contract requires `append` (persist before delivery), `read` (offset-scoped replay and live tail), `snapshot` and `close`. Its `memory:v1` offsets are private to its process-global memory log; a future owner-DB adapter must mint distinct versioned offsets, persist terminal/uncertain stream state, and validate run/session ownership on every read. Returning internal journal cursors as SDK offsets without that adapter would be incorrect. A serialized stream failure leaves the bound run unresolved rather than auto-reexecuting it.

The current `AgentChat` user-node write precedes `liveRuns.claim`, and the existing cross-session `run_id` precheck is not transactional. A real implementation must reserve a bound run in the central owner's SQLite transaction **before** input-node creation; preserve the old `chat_runs`/workflow schema for legacy readers and add new schema steps only at the end of the current migrations list. `ChatState` startup's fail-closed transition also needs worker-generation awareness before a live worker can survive owner restart.

## Compatibility / rollback order (conditional on an additive DB migration)

- Preserve existing chat and workflow tables/IDs; the new immutable Goal-run bindings and owner-only `workflow_run_events` are distinct from Work Trace `run_events`. Wire an authorized central owner and a restart-capable SSE adapter **before** any new worker is allowed to publish. Old paths retain their current semantics until cut over and are guarded by the existing lock and build-ID check.
- Existing run/thread/node/workflow rows remain as-is; no backfill of past in-memory SSE frames is possible. Reconstruct old completed runs from transcript/nodes and mark old unfinished runs failed using current behavior. If a new table is backfilled with metadata only, validate counts, IDs, run/session ownership and terminal states in a transaction before enabling routing.
- DB migrations are appended and atomic (`src/db/migrations.ts`, `src/db/database.ts`). This repo rejects a DB with `user_version` newer than the binary supports. Back up before schema migration: rollback after migration requires a compatible newer-schema reader or restoring a **consistent** backup with new workers stopped; simply relaunching an old binary on the migrated DB is not rollback. Do not delete evidence written since the backup without explicit user acknowledgement.
- Gate checks: real `AgentChat` turn with one central writer and fake provider/tool, duplicate admission, wrong-session/Goal/run denial, commit-before-publish, cursor replay after owner restart, stale worker fencing, crash between tool effect and acknowledgment, old/new Goal protocol overlap, OAuth callback stays central. P03B2/P03B3 cannot be called complete using this document or test-only IPC alone.
