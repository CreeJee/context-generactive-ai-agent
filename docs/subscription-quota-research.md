## Authorization and alternatives

- This app currently requests the [Codex CLI client ID/scopes and ChatGPT backend URL](../packages/memory-agent/src/oauth/protocol.ts), not independently registered Sign in with ChatGPT (SIWC) credentials. OpenAI's [Codex app-server documentation](https://learn.chatgpt.com/docs/app-server.md#auth-endpoints) distinguishes existing local/open-source app-server auth from hosted/commercial use. OpenAI's [SIWC open-source sign-in instructions](https://developers.openai.com/siwc/token-sharing-open-source/sign-in) instead describe dynamic app registration, `resource.invoke chatgpt.tokens.use.direct`, and consent. [SIWC app-server instructions](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server) describe responses integration but do **not** independently guarantee quota fields from this app's current OAuth credential. The [SIWC UI guidance](https://developers.openai.com/siwc/ui-ux-guidelines#link-to-chatgpt-usage) recommends linking to ChatGPT usage settings. An API organization's usage/billing is not a ChatGPT subscription balance.
- This app's Anthropic token uses [Claude Code client ID and `user:inference`/`user:profile` etc., without `org:admin`](../packages/memory-agent/src/oauth/protocol.ts). [Anthropic Usage & Cost Admin API](https://platform.claude.com/docs/en/manage-claude/usage-cost-api.md) and [Claude Code Analytics API](https://platform.claude.com/docs/en/manage-claude/claude-code-analytics-api.md) require admin credentials and measure organization usage, **not personal Claude Pro/Max remaining quota**. [API rate-limit headers](https://platform.claude.com/docs/en/api/rate-limits.md) describe API org/workspace limits, not the personal subscription window.
- **Blocking policy finding:** Anthropic's current [Legal and compliance → Authentication and credential use](https://code.claude.com/docs/en/legal-and-compliance.md#authentication-and-credential-use) states third-party developers may not offer Claude.ai login in their own apps, route Free/Pro/Max credentials on users' behalf, or collect/store/intermediate Claude.ai credentials or session tokens. It distinguishes end users logging into an _unmodified_ Claude Code binary. The existing custom Anthropic OAuth inference/account feature in this project therefore needs a product/legal decision **before further rollout**, not merely a different quota endpoint. No claim of legal authorization is made here.

## Decision gate and verification gap

1. **Do not implement direct `/wham/usage` or `/api/oauth/usage` calls solely from Codex/jcode examples.** Obtain a supported/allowed integration route; test actual A/B-account quota responses without logging secrets, using explicit user-controlled authentication, before declaring any quota field supported. No such test was performed in M4.
2. If a permitted route does not supply a field, return **조회 불가/미확인** with no fabricated number. If a stale response exists, label its observation time and error explicitly; do not substitute locally counted tokens or silently reset elapsed percentages to zero.
3. Confirm how to handle current Anthropic OAuth in light of the official restriction (e.g. supported API-key path or an unmodified Claude Code integration, subject to actual terms). This is a blocking scope/design decision before M5 and UI claims about Claude subscription quota.

**M5 status (2026-10-12, updated after V1):** the user adopted the Anthropic `/api/oauth/usage` route, accepting the policy risk in point 3. `GET /api/accounts/quota?provider=` now returns, per local Anthropic account, the provider's `five_hour`/`seven_day` `utilization` and `resets_at` as `observed` (see [M5 adoption](#m5-adoption-2026-10-12)). OpenAI was later adopted too, through Codex's `/wham/usage` (see [M5 OpenAI adoption](#m5-openai-adoption-2026-10-12)). No local token count is shown as quota.

## V1 — first attempt (2026-10-12): stopped before any call

Superseded by the [app-code V1 run](#v1--app-code-run-2026-10-12-one-request-http-200) below, after the user approved reading the app DB read-only and the refresh risk.

Outcome: **aborted before reading any credential or calling any endpoint.** No token was read, no request was sent to `api.anthropic.com/api/oauth/usage` (or anywhere else), and no new login was started. There is no status, field list or time window to record from a live response.

Why account attribution could not be established without crossing the agreed limits:

1. **The account list lives only in the app DB.** Local Anthropic profiles (IDs, labels, which one is selected) are the `oauth_profiles` metadata read by `listOAuthProfiles({ sqlite, provider })` ([accounts.ts](../packages/memory-agent/src/oauth/accounts.ts)). Each profile's credential is in its own keychain slot `subscription-oauth-<profileId>` under service `com.context-agent.oauth.anthropic`, so the slot names themselves are only known from that DB. Reading the user's app DB was not allowed for this task, and the app has no other code path that lists stored profiles. Listing keychain items by hand was likewise out of bounds. So "exactly one stored Claude account" could not be confirmed, and more than one may exist (M2/M3 support several per provider).
2. **The one slot readable without the DB is ambiguous and shared.** `createKeychainCredentialStore().read("anthropic")` reads the pre-multi-account slot `subscription-oauth`. `importLegacyOAuthProfile` copies that same credential into the `legacy-anthropic` profile slot and never deletes the original. Whether it is the currently selected account cannot be told without the DB. Also, both slots hold the same refresh token: if the access token had expired, the app's refresh would rotate the refresh token and could invalidate the copy the running app actually uses. A "minimal" check could therefore break the user's live login.
3. **No app code for the request exists.** The app has no Anthropic usage client: `SubscriptionQuota` returns `unavailable` for every account by design, and `/api/oauth/usage` appears only in the third-party jcode source cited above. A V1 call would need new code that sends a consumer-login bearer token to an undocumented endpoint, which is exactly the use the [Anthropic credential-use terms](https://code.claude.com/docs/en/legal-and-compliance.md#authentication-and-credential-use) cited in the M4 review restrict.

What would unblock a future V1 (user decision, not done here):

- Choose the account explicitly, either by letting app code read the profile list from the DB (secret-free: profile ID, label, selection) or by the user naming the profile ID. Then read only that profile's slot, with no refresh: if the access token has expired, stop rather than rotate.
- Resolve the M4 policy finding first. A successful response would still be evidence only. M5 stays `unavailable` (`provider_policy_restricted` for Anthropic, `no_permitted_route` for OpenAI) unless the user decides to adopt a route.

## V1 — app-code run (2026-10-12): one request, HTTP 200

The user approved V1, including the risk that a token refresh could disturb the current login. Only app code touched the DB and credential: [`eval/anthropic-usage-probe.ts`](../packages/memory-agent/eval/anthropic-usage-probe.ts) calling [`anthropicSubscriptionUsageProbe`](../packages/memory-agent/src/oauth/subscription-usage-probe.ts). No secret, email, token or response value was printed or recorded.

- **DB access:** `Database.layer` cannot open read-only (every open sets WAL and runs `migrateDatabase`, which starts `BEGIN IMMEDIATE` and `CREATE TABLE IF NOT EXISTS effect_sql_migrations`). The probe therefore uses the app's existing read-only path from `eval/live-delegation.ts`: `new DatabaseSync(~/.context-generactive-agent/agent.db, { readOnly: true })` + `listOAuthProfiles({ provider: "anthropic" })`. No migration and no DB write.
- **Account attribution:** exactly one Anthropic profile, so the probe proceeded: profile ID `legacy-anthropic`, label "Claude (이전 계정)", `selected: true`. Its credential was read from that profile's keychain slot via `createKeychainProfileCredentialStore`.
- **Token:** the stored access token was still valid (app margin: expires more than 30 s ahead), so **no refresh happened** and nothing was written to the keychain.
- **Request:** exactly one `GET https://api.anthropic.com/api/oauth/usage` with the app's Anthropic OAuth headers and bearer, no retry. **Status 200.**
- **Top-level fields (names only):** `five_hour`, `seven_day`, `seven_day_oauth_apps`, `seven_day_opus`, `seven_day_sonnet`, `seven_day_cowork`, `seven_day_omelette`, `tangelo`, `iguana_necktie`, `omelette_promotional`, `nimbus_quill`, `cinder_cove`, `copper_kite`, `brass_thimble`, `harbor_lantern`, `wattle_ember`, `amber_ladder`, `amber_cistern`, `juniper_tide`, `cedar_ember`, `amber_gauge`, `extra_usage`, `limits`, `spend`, `member_dashboard_available`, `seven_day_breakdown`, `weekly_scoped_shares`.
- **Windows** (objects whose `utilization` was a number or null in this response):
  - `five_hour`, `seven_day`, `iguana_necktie`: `utilization`, `resets_at`, `limit_dollars`, `used_dollars`, `remaining_dollars`, `locked_reason`.
  - `extra_usage`: `utilization`, `is_enabled`, `monthly_limit`, `used_credits`, `currency`, `decimal_places`, `disabled_reason`, `user_disabled`, `spend_limit_reached`, `credits_ever_enabled`, `daily`, `weekly`.
  - The other `seven_day_*` fields and the code-named fields were not window objects in this response (for example `null`), so their shape is unobserved.

What this shows and does not show:

- The endpoint answers this app's stored consumer-login token with provider-reported `five_hour`/`seven_day` utilization and reset times, matching the jcode parser. It is one observation of one account; the schema is undocumented and has many code-named fields that may change without notice.
- It does **not** resolve the M4 policy finding: the call is exactly the third-party use of Claude.ai credentials that Anthropic's credential-use terms restrict.
- At the time of this run M5 was unchanged; the user then adopted the route (next section).

## M5 adoption (2026-10-12)

The user decided to show Anthropic quota from this route despite the credential-use terms finding above. [`SubscriptionQuota`](../packages/memory-agent/src/oauth/subscription-quota.ts) reads it through `anthropicSubscriptionUsage` in [subscription-usage-probe.ts](../packages/memory-agent/src/oauth/subscription-usage-probe.ts):

- **Windows:** only `five_hour` (18 000 s) and `seven_day` (604 800 s), each only when `utilization` is a number. `usedPercent` is that `utilization`; `resetsAt` is `resets_at`. Code-named and dollar fields are ignored.
- **No refresh:** the lookup reads each profile's stored access token and never refreshes it. An expired token fails the lookup without a request, so it never races the model path's refresh of a rotating refresh token.
- **Rate:** at most one request per account per minute (`Cache` with a 1-minute TTL); concurrent sidebar reads share it, and at most two accounts are looked up at once.
- **Failure:** a failed lookup returns the last observation as `stale` (with `failedAt`), never zero. With no earlier observation it returns `unavailable` with `credential_expired` (token expired) or `lookup_failed` (any provider, transport or shape failure). Only the error tag is logged.
- The previous `provider_policy_restricted` reason is removed; the route was never in a GitHub release.

## M5 OpenAI adoption (2026-10-12)

- Decision: the user adopted Codex's ChatGPT backend route for OpenAI accounts. Anthropic keeps `/api/oauth/usage` unchanged.
- `openAiSubscriptionUsage` sends one `GET https://chatgpt.com/backend-api/wham/usage` per account with the stored access token and the `chatgpt-account-id` header, the same headers the model catalog uses. Like Anthropic, it never refreshes an expired token (`credential_expired`) and never retries.
- Only `rate_limit.primary_window` and `rate_limit.secondary_window` are read: `used_percent`, `limit_window_seconds` and `reset_at` (Unix seconds, shown as ISO). They become the windows `primary` and `secondary`; the sidebar labels them by length (for example 5시간, 7일). `plan_type`, credits and other fields are ignored.
- The field names come from the Codex backend client cited above. No live response was inspected in this change, so the first real lookup is the verification. If the shape differs, the account shows `lookup_failed` rather than a guessed number.
- `no_permitted_route` was removed; it was never in a GitHub release.
