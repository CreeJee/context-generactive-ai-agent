# 기억 검색 측정 (2026-10-30~)

실제 기억 DB 사본으로 잰 기억 검색의 지연·실패율·정확도다. 결정은 [decisions.md](decisions.md)에 남기고, 여기에는 숫자와 재는 방법을 둔다.

## 재는 방법

- 사본: 사용자가 `~/.context-generactive-agent`의 `agent.db`(`.backup`), `vectors/`, `models/`를 `/tmp/cga-bench`에 복사했다. 샌드박스가 `/tmp`에서 SQLite `-shm` 파일을 만들지 못해 `bench-copy-stage` 스킬로 git이 무시하는 `node_modules/.vp-tmp/cga-bench`에 옮겨 쓴다. 사본과 결과 파일(`*.jsonl`)은 커밋하지 않는다. 작업이 끝나면 두 사본을 지운다.
- 규모: 노드 276,162개, 벡터 63,671개(현재 embedder), 측정 프로젝트(대화 프로젝트) 노드 26,762개, 기기 M1 Pro.
- 지연: `eval/native-read-bench.ts`(`native-read-bench` 스킬). 네이티브 read 하나를 앱과 같은 입력으로 돌린다. 2초 예산, `textK`=limit×2, `vectorK`=min(limit×4, 48). 벡터는 무작위 단위 벡터(단계 비용은 벡터 값과 무관). morph는 기본으로 꺼 두고, `--morph`를 주면 DB 옆 `models/`의 Kiwi로 질의마다 앱과 같은 형태소 검색어를 만들어 켠다(2026-11-05부터).
  - find: 기록된 `find_memory` 질의 60개(최근, 중복 제거), 물은 프로젝트 하나만, limit 12.
  - interpret: 사용자 발언 앞 500자 40개, limit 10.
  - recall: 같은 세션의 사용자 발언 세 개를 이은 6000자 이하 질의 29개, limit 16.
  - cold: 새 read 세션의 첫 read(SQLite 페이지 캐시가 빔, OS 파일 캐시는 남을 수 있음). warm: 같은 세션에서 바로 다시.
- 정확도: `eval/relevance.ts`(`relevance-eval` 스킬). 아래 S3 절 참고.

실패한 read 91개가 멈춘 곳:

- 두 글자 검색어 `instr` 스캔 안: 84개(find 6, interpret 39, recall 39). 멈출 때 돌던 검색어 하나가 이미 36~2050ms(중앙값 약 1550ms)를 썼다.
- trigram 쿼리 안: 2개(recall, 검색어 수백 개).

읽은 것:

- 원인은 두 글자 검색어 스캔이다. 드문 검색어 하나가 최신 행부터 DB 전체(노드 27만, 원문 3.6GB)를 훑어 0.7~1.8초를 쓰고, 질의마다 검색어 수만큼 반복한다. warm에서도 비슷해 IO보다 원문 읽기와 `instr` 비용이 크다.
- 실제 `find_memory` 질의는 짧아 실패가 5~7%지만, interpret(500자)와 recall(6000자)은 절반 넘게 실패한다. 자동 recall은 지금 대부분 빈손이다.
- 벡터 단계(후보+벡터)는 p95 100ms 아래로 원인이 아니다.
- 이 bench는 대기(`queueMs`)가 없다. 앱에서는 한 worker가 read를 차례로 돌려 대기가 더해진다.

## S3 관련성 세트

`eval/relevance.ts build`로 사본의 기록에서 만든다(`relevance-eval` 스킬). 세트 파일은 사본 폴더(`relevance.jsonl`)에만 있다.

- 규칙: 기록된 `find_memory` 호출 하나가 질의다. 그 결과에 있던 노드 중 같은 run이 다음 `find_memory` 전에 `read_evidence`나 `trace_evidence`로 연 것이 정답이다. 아무것도 열지 않은 호출은 뺀다. 같은 질의·프로젝트는 하나로 합친다.
- recall 항목: 같은 호출 앞의 사용자 발언 세 개를 이어 6000자 이하로 자른 질의, 정답은 같다, limit 16.
- 크기: `find_memory` 기록 548회에서 find 202개, recall 174개. 항목당 정답 1.38개.
- 한계: 그때 검색이 돌려준 노드만 정답이 될 수 있어서, 다른 좋은 노드를 찾는 변경은 점수에 드러나지 않는다. 계획에 있던 정정(corrects) 기록은 질의를 만들 마땅한 규칙이 없어 넣지 않았다.
- 채점: 앱과 같은 `MemorySearch.find`(사본 벡터와 같은 fp32 임베딩, Kiwi 포함). 시작 때 벡터 채우기와 GPU 점검은 끈다(사본에 쓰다 실패하면 색인이 막힌다). 실패한 검색은 0점으로 센다.

## 대기 시간 (queueMs) (2026-10-30)

네이티브가 잰 대기 시간(호스트가 SearchControl을 등록한 뒤 worker가 claim하기까지)은 두 벤치 결과 파일의 모든 성공 read에서 0이었다: s5-index.jsonl 255개 성공, s7s9-index.jsonl 516개 성공, p50=p95=max 0ms. 벤치는 등록 직후 같은 흐름에서 read를 호출하므로 대기가 생기지 않는다. 앱 실행의 대기 분포는 따로 재지 않았다. S10 결정(decisions.md 2026-10-30)은 이 수치와 기록된 실패가 전부 text 단계 예산 초과였다는 사실로 예산 시작 시점(등록 시점)과 크기(2000ms)를 그대로 두기로 했다.

- cold와 warm의 차이가 S2 때보다 작아졌다. 페이지 캐시가 질의 사이에 남으면 더 줄어든다. 시작 때 데우기는 시도하지 않았다: cold p95가 이미 0.5초 아래라 2초 예산의 여유가 크다.

### (4) 4-bit 양자화 손실 — 수치만 기록, 변경 없음

`quantization-loss` 스킬(`eval/quantization-loss.ts`): 사본의 최다 프로젝트에서 최신 노드 2,000개 원문(4,000자까지 자름)을 다시 임베드해(사본 벡터와 같은 fp32 변형) 새 4-bit 인덱스에 넣고, 같은 벡터에 대한 정확 내적 순위와 4-bit 순위를 질의 40개(S3 세트 질의를 우선 사용)에서 비교했다.

- overlap@5 1.000, overlap@12 0.892, top1 동일 82.5%, 정확 1위가 4-bit 상위 12에서 빠진 경우 0(빠지지 않았을 때 평균 순위 1.18), 점수 차이 평균 2.2e-3·최대 9.2e-3.
- 속도: 4-bit 검색 0.07ms, 정확 내적 2.93ms(2,000 벡터, 질의당).
- 해석: 4-bit 양자화는 상위 5개를 그대로 유지하고 12위 안에서 약 11%를 밀어낸다. 2026-10-18 결정(CPU quint8 / GPU fp32, turbovec 4-bit)대로 양자화는 바꾸지 않는다.

### (1) vectorCut 0.1 — 기각

`--tuning '{"vectorCut":0.1}'` — 1위 벡터 점수보다 0.1 낮은 벡터 히트를 잘라 다른 채널이 밀어내도록 한다(채널별 상한이 걸린 실제 사용 질의에는 벡터 목록이 늘 잘리지 않아 거의 무차이로 예상했다).

- 결과: find MRR 0.236(기준선 0.235), Recall@5 0.267(0.273), Recall@12 0.385(0.391); recall MRR 0.085(0.083), Recall@5 0.117(0.118), Recall@16 0.171(0.164). 실패 0.
- 항목별(find 202쌍): R@12 나음 0·나쁨 2(합 −1.25), R@5도 나쁨. recall 174쌍: R@16 나음 3·나쁨 2(합 +1.17).
- 판정: 채택 기준(두 세트 어디에서도 기준선보다 낮지 않다)을 find 그룹의 R@5·R@12 하락으로 통과하지 못해 기각한다. recall의 작은 이득은 find의 손실을 메지 않는다. vectorCut 0은 그대로 둔다.
- 덤범 행의 degraded 개수는 실행마다 달랐다(기준선 recall text 3행 → 이 실행 5행+morph·other-projects 1행씩). degraded는 예산 근처 read의 타이밍 변동으로 생기는 것이고 튜닝이 원인이 아니라, 비교는 MRR·Recall@k로 한다.

### (2) vectorWeight 2 — 채택(단독), 기본값에 반영

`--tuning '{"vectorWeight":2}'` — 일반 융합(정확 이름 질의가 아닐 때)에서 벡터 채널의 RRF 가중치를 1→2로 올린다. 4비트 양자화와 자르기 없는 벡터 목록이 항상 꽉 차 있어 다른 채널에 밀려 상위에서 빠지는 관련 노드를 되살린다. `exactFirst` 경로(정확 이름 질의)는 고정 가중치 2/1/1을 쓰고 이 값을 읽지 않는다.

- 결과: find MRR 0.245(기준선 0.235), Recall@5 0.284(0.273), Recall@12 0.399(0.391); recall MRR 0.087(0.083), Recall@5 0.118(0.118), Recall@12 0.138(0.136), Recall@16 0.164(0.164). 실패 0.
- 항목별: find 202쌍 reciprocal 나음 13·나쁨 6(합 +2.16), R@12 나음 7·나쁨 5(합 +1.58), R@5 나음 4·나쁨 2(합 +2.25); recall 174쌍 reciprocal 나음 5·나쁨 2(합 +0.68), R@16 나음 1·나쁨 1(합 0).
- eval:recall(`vector(quint8) + trigram + kiwi`, 기준선 24/29/30 0.836 · 19/22/22 0.759): decisions 24/30/30 0.844, technical 19/22/22 0.759 — 하락 없음.
- 판정: 채택. `searchTuning.vectorWeight`를 2로 바꿨다(2026-10-31). 첫 실행(작업 4d110c76)이 1500초 제한에 걸쳐 277/376행에서 끝겼고 `--resume`(작업 4048b9a9)으로 나머지를 채웠다(실패 0).

### (3) otherProjectMerge append — 단독 기준 통과, 기본값에는 미반영

`--tuning '{"otherProjectMerge":"append"}'` — 다른 프로젝트의 text·morph 순위 목록을 자기 프로젝트 목록 뒤에 이어 붙인다(지금은 alternate: 모든 목록의 1위, 2위…를 번갈아 섞는다). 다른 프로젝트 결과는 자기 프로젝트 후보가 부족할 때만 뒤를 채우는 역할이 맞다는 발상이다.

- 결과: find MRR 0.239(0.235), Recall@5 0.302(0.273), Recall@12 0.441(0.391); recall MRR 0.090(0.083), Recall@5 0.128(0.118), Recall@16 0.180(0.164). 실패 0.
- 항목별: find 202쌍 R@12 나음 17·나쁨 6(합 +10.0), R@5 나음 10·나쁨 5(합 +5.8); recall 174쌍 R@16 나음 7·나쁨 4(합 +2.67), R@5 나음 4·나쁨 2.
- 판정: 단독으로는 채택 기준을 통과한다. 그러나 vectorWeight 2와의 결합에서 find MRR이 기준선 밑으로 내려갔다(아래 '(2)+(3) 결합'), 기본값은 결합을 전제로 정하므로 `searchTuning`의 otherProjectMerge는 "alternate"를 유지한다(2026-10-31).
- 참고: 첫 실행(작업 9147b8c3) 중 서버 재시작으로 앞 프로세스의 CacheLease 점유 구간과 겹쳐 14행이 budget-exceeded(morph 단계, ~2000ms)로 기록됐다. 이 튜닝은 read 비용을 바꾸지 않는 융합 단계 변경이라 환경 문제이고, 14행을 덤프에서 지운 뒤 `--resume`으로 다시 채점해(작업 859fe767) 실패 0의 최종 수치를 얻었다.

### (2)+(3) 결합 vectorWeight 2 + otherProjectMerge append — 기각

`--tuning '{"vectorWeight":2,"otherProjectMerge":"append"}'` — 채택한 두 후보를 함께 넣으면 나아지는지 보기 위한 결합 채점.

- 결과(376행, 실패 0): find MRR 0.230(기준선 0.235, vw2 단독 0.245), Recall@5 0.285(0.273), Recall@12 0.439(0.391); recall MRR 0.088(0.083), Recall@5 0.120(0.118), Recall@12 0.166(0.136), Recall@16 0.191(0.164).
- 항목별(기준선 대비): find reciprocal 나음 17·나쁨 47(합 +0.93), R@12 나음 12·나쁨 26(합 −9.7); recall reciprocal 나음 7·나쁨 14(합 −0.8). find MRR이 기준선 밑으로 내려가 채택 기준을 통과하지 못한다.
- 원인: append 단독이 find 202쌍에서 기준선 대비 잃은 12쌍 중 5쌍은 1위였던 답을 잃은 쌍이고 그중 2쌍(89479e4832d4, 2b5373ff8a8c)은 상위 16에서 완전히 빠졌다. vw2 단독은 이 다섯 쌍을 모두 유지했다. 결합은 append의 1위 손실에 vw2의 벡터 밀어올림이 더해져 MRR 이득을 지웠다(결합 vs vw2 단독: find reciprocal 나음 18·나쁨 39).
- 판정: 기각. 두 후보를 함께 넣을 수 없으므로 vectorWeight 2만 `searchTuning` 기본값에 반영하고 otherProjectMerge는 "alternate"를 유지한다(2026-10-31). append는 (3)의 채택 판정을 결합 결과로 갈아엎지 않는다: 평가 목적은 기본값 구성이고, 채택 기준은 "두 세트 어디에서도 기준선보다 낮지 않다"를 기본값이 통과해야 한다는 뜻으로 읽는다.
- 실행 기록: 서버 재시작 두 번(사용자 요청) 사이에 --resume으로 이어 채점했다(작업 9b63507b → e8e01469 → 829e2d39(중단) → c7815f5c → f9330d18). 재시작 사이에 죽은 프로세스가 덤프에 남긴 budget-exceeded 51행(기준선·vw2 실패와 0 겹침)과 14행(전부 재실패)은 매번 지우고 백업(s9-dump-vw2opm.failed-51.jsonl, s9-dump-vw2opm.failed-14.jsonl)했다. 마지막 실패 1행(coverage 단계)도 지우고 재개해 실패 0으로 마쳤다(s9-dump-vw2opm.failed-1.jsonl).

### 채점 도구 개선 (2026-10-30)

- `relevance-eval score --dump <파일>`이 행이 끝날 때마다 덤프에 덧붙인다(전에는 끝에 한 번 써서 진행을 관찰할 수 없고 죽으면 전부 잃었다). `--resume`은 덤프에 이미 있는 항목을 건너뛰고 이어서 채점한다. 요약 표는 항상 덤프 전체를 읽어 계산한다(마지막 행 우선). 376행 한 번의 채점은 실규모 read로 10분 이상 걸려, 한 번의 run_skill 시간 제한을 넘기면 같은 인자에 `--resume`을 얹어 이어 돌린다.
- 채점은 저장소의 CacheLease를 독점하므로 동시에 둘 이상 돌리면 두 번째가 lease-unavailable로 즉시 실패한다(확인됨). 후보 채점은 하나씩 순서대로 돌린다.
