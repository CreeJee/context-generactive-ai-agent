# Local semantic recall sensor: S1 feasibility and contract

Status: S1 investigation. No Laya installation, automatic recall, or model integration is enabled by this document.

## Existing boundaries (2026-10-04)

- `packages/memory-agent/src/agent/chat.ts` handles new user turns separately from internal follow-ups and tool/approval continuations; redacted user text is persisted as evidence. A new recall sensor must run at most once per admitted new turn, never as a side effect of every provider continuation. The external-agent branch uses a separate `memoryPreamble`; do not change that branch in this experiment.
- `packages/memory-agent/src/agent/compaction.ts` prepares each model-bound request, but calls `retrievalAppendix` only when original content was omitted (`stage !== "none"`). The appendix is best-effort and inserted before the latest user message. The new-turn trigger is not a substitute for this behavior; shadow mode must not change its provider-bound messages or durable evidence.
- `packages/memory-agent/src/memory/search.ts` performs project-scoped vector/text/morph rank fusion followed by graph traversal. The existing manual `find_memory`, `read_evidence`, and `trace_evidence` tools remain independent. A trigger score is **not** a ranked node list for RRF. A future automatic search must explicitly pass `crossProject: false` rather than relying on `find`'s cross-project default.
- Local embedding uses a CPU or WebGPU model (`packages/memory-agent/src/memory/embedding/embedder.ts`); its concurrent memory, accelerator and energy contention with another local model needs measurement before activation.

## Contract for a future, replaceable sensor (design only)

1. **Input:** a single admitted new user turn, redacted/minimized text and only the allowed recent same-project context needed to resolve deictic references. No full tool results, cross-project history, credentials, attachments, or opaque model-provider prompts. The input budget is bounded; neither raw evidence nor approved user decisions may be altered.
2. **Output:** `disabled | skipped | unavailable | timeout | error | evaluated`, and for an evaluated turn a finite _uninterpreted score_ and model/runtime version, plus elapsed time. Do not describe it as a calibrated probability; do not fix a threshold before validation. Store only bounded, non-content telemetry in shadow mode, if any; no message/evidence/graph-edge mutation.
3. **Trigger:** decides only whether a search _might_ be useful. Query construction from permitted recent context is separate. Candidate-relative hints such as `retracts_candidate` require retrieved candidates and must not create `corrects`/`retracts` edges or user decisions.
4. **Failure:** disabled, unsupported hardware, low-resource mode, cancellation, timeout and other failures all mean _no new automatic search_. Existing provider request, compaction appendix, external-agent preamble, and manual tools retain their existing behavior. Stop the local process on shutdown; avoid duplicate evaluation for continuations of the same turn.
5. **Locality:** default no remote endpoint or silent model download. If the verified distribution requires a service, it must run only on the same user machine, bound to loopback, with managed lifetime and cleanup. Explicit user opt-in is required before any nonlocal transfer/download; errors must not fall through to a cloud service.

S2 will define the thresholds, hardware and evaluation budgets using measured data rather than example values. S3 may implement this contract only after the feasibility review below identifies a suitable local artifact.

## Distribution feasibility — upstream v0.3.26, documentation review (2026-10-04)

The candidate is [NandhaKishorM/laya](https://github.com/NandhaKishorM/laya), **not an arbitrary same-named package**. [Release v0.3.26](https://github.com/NandhaKishorM/laya/releases/tag/v0.3.26) and [PyPI v0.3.26 metadata](https://pypi.org/pypi/laya/0.3.26/json) identify a Python >=3.10 universal wheel (`laya-0.3.26-py3-none-any.whl`, 312,721 bytes) and source archive. The wheel does **not** include model weights or establish native GPU support. Upstream [LICENSE](https://github.com/NandhaKishorM/laya/blob/v0.3.26/LICENSE) and model cards ([English](https://huggingface.co/convaiinnovations/laya), [multilingual](https://huggingface.co/convaiinnovations/laya-multilingual), [typed decisions](https://huggingface.co/convaiinnovations/laya-typed-decisions)) show Apache-2.0; dependency licenses remain unaudited. Pin package and checkpoint revision/digest for reproducible evaluation.

[Installation instructions](https://github.com/NandhaKishorM/laya/blob/v0.3.26/README.md#installation-details) include macOS/Linux, Windows PowerShell and PyTorch-dependent CPU/GPU paths. [Container platform notes](https://github.com/NandhaKishorM/laya/blob/v0.3.26/docs/docker-platforms.md) report Linux AMD64/ARM64 CPU validation, AMD64 NVIDIA inference, and ARM64 DGX Spark build/library checks (not a Spark inference run). Apple Silicon Docker is Linux ARM64 CPU; MPS needs native macOS. This development host reports Darwin arm64 / macOS 27.0 (`uname -sm; sw_vers -productVersion`); this is **not** a Laya compatibility test or a promise about another user's hardware. No packages/models were installed or run.

[HTTP configuration](https://github.com/NandhaKishorM/laya/blob/v0.3.26/docs/http-api.md) documents `python -m pip install "laya[serve]"` and `LAYA_HOST=127.0.0.1 LAYA_MODELS=multilingual LAYA_PRELOAD=0 laya-serve` as a _proposed_, not executed, single-machine sidecar path. Bare `laya-serve` defaults to **0.0.0.0** and preloading. A loopback process still needs bind verification, lifetime/shutdown management and access control (no `LAYA_API_KEY` by default). [Docker serving](https://github.com/NandhaKishorM/laya/blob/v0.3.26/docs/docker.md#http-serving) offers a loopback-published alternative, not a separate server. The upstream `laya-ts` ONNX browser/Node port needs exported weights; it is not the chosen path and a published npm release was not verified.

`POST /v1/systemone` accepts `state` and a **question-ID-keyed object** of typed `questions`; responses likewise use an `answers` object keyed by question ID ([API](https://github.com/NandhaKishorM/laya/blob/v0.3.26/docs/http-api.md#post-v1systemone)). The mock HTTP adapter in `packages/memory-agent/src/agent/recall-sensor.ts` was corrected to this documented v0.3.26 shape; it has not been verified against a running server. `noul` is the probability of yes, **not** a boolean; `choice` returns a label/distribution; `score` is an expected **ordered-level index**, **not** a probability. `confidence` and `answer_confidence` are distinct. [Upstream confidence guidance](https://github.com/NandhaKishorM/laya/blob/v0.3.26/docs/questions-and-answers.md#reading-confidence) says shipped checkpoints are overconfident and not calibrated for callers' traffic. S2/S4 must select a typed question/checkpoint and evaluate any threshold on held-out turns. Do not map `score` to `P(memory_required)` or adopt an illustrative `0.35` threshold.

[Model setup](https://github.com/NandhaKishorM/laya/blob/v0.3.26/README.md#model-setup-and-troubleshooting) says checkpoints download from Hugging Face on first use; `HF_HUB_CACHE` configures a cache and `HF_HUB_OFFLINE=1` requires pre-staged weights or fails. Installation itself requires package/dependency acquisition unless staged. Default checkpoint revision and total download size are **not** pinned/measured. Stage an approved pinned checkpoint in a dedicated cache before any offline-mode trial. External forwarding hooks and browser demos are excluded. We have **not** packet-captured the process or verified absence of telemetry/network calls; this remains an S3 gate. On removal, stop the managed process and remove only its dedicated environment/cache after verifying ownership, not a shared Hugging Face cache. Upstream Docker documents `docker compose down --volumes` for its own cache volume; host removal is a proposed procedure, not a verified upstream uninstall command.

**Implementation status after S2/S3 preparation:** a default-unconfigured shadow hook accepts a sensor only when explicitly supplied to `makeAgentChatImplementation`; production passes none. The hook discards scores and never triggers search or changes provider messages. The isolated adapter is default-disabled, and no UI setting or automatic local-process startup exists. It must not be turned on for real turns until resource admission, measured offline operation and user consent are in place.

**S1 decision:** the documented local Python loopback configuration is plausible for a shadow experiment, but not yet runtime-validated on this machine. Do not install/start it, send user text, or enable automatic search until model-download consent, offline/bind checks, resource measurement and fallback are verified. If these fail, retain mock/heuristic evaluation only. Source review proves configuration claims, not runtime behavior.
