# Local recall sensor evaluation protocol (S2)

Status: measurement design, not measured Laya performance or permission to download its weights. The S1 source/contract review is in [laya-recall-s1.md](laya-recall-s1.md). This experiment leaves existing search and manual evidence tools unchanged.

## Dataset and labels

The synthetic fixture `packages/memory-agent/eval/recall-turns.fixture.json` provides project-tagged prior evidence, `recentTurns` (currently the incoming user turn), `recallNeeded`, candidate `searchEvidenceIds`, and gold evidence IDs. `searchEvidenceIds` may deliberately contain wrong-project decoys, which must be excluded by project scoping. A needed turn must require **prior evidence not already visible in the current provider input** to answer correctly; a mere mention of history is not sufficient. A correction/withdrawal needs both the earlier claim and later correction (or a provenance edge) to avoid asserting the obsolete decision. Independently label the trigger, query suitability, retrieved top-K evidence and what the answer actually uses. No real user's memory is bundled. Use frozen validation/holdout splits grouped by synthetic scenario family, not near-duplicate paraphrases split across sets; development cases are not used for threshold selection. Expand and adjudicate disagreement before treating the fixture as a representative benchmark. Existing `packages/memory-agent/eval/recall.ts` measures search ranking separately and is not a turn-level trigger baseline.

Replay each fixture through four policies using the same preexisting synthetic evidence snapshot and same query construction: compaction-only (current behavior), fixed simple heuristic (explicit prior-reference/correction phrases), search every eligible turn, and shadow Laya. Disabled/timeout cases count as no new automatic search. For each turn record `triggered`, `query`, final ranked candidate IDs, gold IDs present at K=5/10/16, project scope, superseded markers, query-construction failure, and whether an answer uses the correct original/provenance. A trigger hit that yields no gold evidence is **not** a recall success. Direct score comparisons between `noul`, `choice`, and `score` are invalid; fix the checkpoint, question type, instructions, and context budget before tuning. Select a threshold only on validation; freeze it before evaluating untouched holdout. Calibration checks compare binned `noul` yes frequencies to observed labels and stratify by language/type; score semantics never imply calibrated probability.

For answerable needed turns (nonempty gold), define needed-turn coverage = turns with all required gold evidence accessible in top-K / answerable needed turns; unnecessary-search rate = unnecessary turns triggering search / unnecessary turns; query failure rate = triggered answerable needed turns missing gold / triggered answerable needed turns; source error rate = decisions stated from superseded/unconfirmed or wrong-project sources / evaluated answers. Unanswerable history requests (empty gold) are reported separately as abstention/no-hallucination cases, never counted as retrieved gold. Report absolute counts, intervals and per-scenario failures as well as the deltas versus compaction-only and simple heuristic. Report precision/cost too; always-search is an upper-bound reference for trigger recall, not a deployment target. Holdout gate: improve gold-evidence coverage over the best acceptable baseline **without** violating any privacy/correctness/resource bound; if the sample cannot resolve a meaningful improvement, remain in shadow. Do not promote model hints to graph edges or user authority.

## User-machine resource protocol and provisional limits

The trial matrix is baseline idle, existing local embedding alone (CPU then WebGPU when supported), sensor alone (cold start then warm), and concurrent embedding+sensor. Repeat short/long Korean and English turns under the same platform/thermal/power state, and sample process-tree RSS/peak memory, CPU percent, GPU use when observable, disk cache bytes, cold/warm p50/p95 elapsed time, and battery discharge or energy impact (on battery only; indicate if unsupported). Record CPU architecture/OS, total/free RAM, selected device, model/checkpoint and revision/digest, weight/cache download bytes, process startup/shutdown and post-idle resident memory. Count model setup/download separately from inference; no downloads or network observation without explicit user approval. Run a no-network test with weights pre-staged and `HF_HUB_OFFLINE=1`, and verify loopback-only listeners/egress on a supported host before transmitting private turns. Real-user shadow observation uses only bounded non-content metrics after the local trial passes.

Provisional **activation gates**, not empirical claims: the default remains disabled; warm sensor overhead p95 <= 250 ms over the same baseline and cold-to-ready <= 2 s on the target machine, otherwise skip instead of blocking chat. Cap optional per-turn input at 512 local tokenizer tokens (or a smaller tested limit); no attachments or tool bodies. Abort/skip when estimated available memory after launching would be below 20% of installed RAM or 1 GiB (whichever larger); never run on battery-saver/low-power mode or if the model would contend with an active embedding job and exceed the latency gate. A dedicated cache must have an explicit maximum approved download/disk size (unknown until checkpoint metadata/actual transfer measured); no silent download. Require no unauthorized egress, no sustained idle process if configured to unload, and negligible additional battery drain within measurement uncertainty. These are proposed safety ceilings, not a promise that Laya meets them; adjust only after reporting machine-specific evidence and before enabling search. Shadow may finish without meeting the automatic-search gate, but S5 must not proceed in that case.

Smallest checks: fixture schema/gold-ID/project boundary validation, pure-policy replay, mock sensor fallback. Then search/compaction/agent-chat regression and existing recall evaluation. No model weights, local server or background sensor are introduced by this protocol.
