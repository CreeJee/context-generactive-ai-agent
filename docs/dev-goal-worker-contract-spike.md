# Dev Goal worker contract spike (not a design decision)

## Historical status (2026-10-03)

This document preserves the original experiment and its then-current limitations; statements about the runtime below are not a description of today's implementation. The self-owner `dev-goal-worker-contract.test.ts` and sole-use `fixtures/dev-goal-worker.ts` were removed under Plan v15 after actual AgentChat/SDK worker/HTTP/OAuth replacement regressions passed. They only checked local maps, token comparisons and hardcoded service counts, not production safety. The useful Vite and worktree hazard tests remain. See [cleanup classification and replacement coverage](dev-cleanup-effect-regressions.md) and [current owner execution contract](dev-goal-owner-execution-contract.md).

## Observed on 2026-09-30

- `dev-goal-isolation.test.ts`: a Git worktree alone omits dirty and untracked code; explicit per-Goal copies keep later imports isolated. Concurrent complete backends cannot share the existing storage owner lock. Separate storage roots make projects/sessions invisible across processes (also observed against two packaged backends in temporary storage).
- `dev-goal-worker-contract.test.ts` and `fixtures/dev-goal-worker.ts`: two **test-only** Node child processes can perform a late import from different Goal code directories while a parent owns a mock session→Goal binding, one mock embedding service and one mock OAuth listener. The parent denies wrong session/token, stale Goal, duplicate run ID and wrong-worker RPC. A previously accepted old-Goal run finishes on its original worker after a new Goal begins. The parent retains events for replay. This tests an IPC shape, **not** a real agent turn, persistent database, embedding engine, OAuth exchange, SSE reconnect or crash recovery.
- The real composition root (`packages/memory-agent/src/layers.ts`) creates `AgentChat` along with Database, Workflows, ChatState, MemorySearch/Indexer/Embedder, providers, approvals, tools, queues and external agents in a single Effect layer. `AgentChat.make` (`src/agent/chat.ts`) eagerly captures these services and owns an in-memory live-run map. `apps/agent/app/routes/api/chat.tsx` calls that single `AgentChat` directly for hydration and streaming; `/api/sessions/:session` calls it for status and workflow control. The current runtime does **not** expose an execution-only worker service or an owner↔worker RPC. Rehosting the existing `AgentChat` unchanged in each child would re-create the very storage/embedding/OAuth owners this spike must avoid.

## P03B0 real-service boundary check (2026-10-01)

- `packages/memory-agent/tests/agent-chat-goal-boundary.test.ts` uses the **real `AgentChat` and DB service graph**, a temporary storage root and a gated fake provider. It verifies that one running turn rejects a duplicate admission (409), writes one persisted run and one user/assistant node, and replays its answer on same-owner SSE hydration. This baseline has **no worker process** and does not prove Goal generation routing, process restart, remote writes, OAuth callback ownership or retry safety. The test initially supplied `offset=0`, which TanStack's `memoryStream` rejects; `offset=-1` is the valid replay-from-start offset.
- In `layers.ts:127-265`, `memoryAgentLayer(storageRoot)` constructs Database, VectorIndex, Embedder, ChatState, Workflows, provider registry and AgentChat in one layer. In `chat.ts:368-412` the real `AgentChat.make` captures the raw SQLite handle, nodes, tools, providers, workflows, queue and leases in closures. In `chat.ts:862-940,1011-1029,1156-1168,1366-1389`, admission, persisted user write, in-process `liveRuns.claim`, model/tool execution and SSE stream ownership are one handler. `live-runs.ts` holds a per-process Map. `chat.ts:1411-1430` rejoin checks DB run existence then uses the process's memory-stream adapter, not an owner-persisted cross-process log. Therefore **placing the current `AgentChat` in a Goal worker unchanged cannot satisfy central-only DB/embedding/OAuth ownership or survive a worker restart while preserving the run**. Sending only model calls to a worker leaves Goal-sensitive tool and workflow code in the mutable central server.
- No real owner↔worker AgentChat turn has been run. To cross this boundary without unsafe shared writers requires a new execution/runtime interface plus central transactional/admission and event RPC: separate turn admission and user-node write from worker execution; explicitly bridge reads and tool/provider effects; pin source and RPC schema for live Goals; durably bind run+Goal and event cursor; handle an uncertain post-side-effect worker death. This is a multi-service refactor, not a routing setting. The existing build-ID 409 gate and single storage owner must remain until that integration exists and passes crash/OAuth tests. No schema migration or backfill was attempted. For a future schema change, upgrade central read compatibility before worker writers, keep old Goal RPC readers/writers supported until drained, backfill with validation, and roll back the new worker before reverting central schema; a breaking DB rollback cannot occur with old Goals still active.

## Minimal boundary to prove before production implementation

1. Only the central server holds the storage owner lock, database/transaction writer, vector index, embedding model, OAuth callback/PKCE state and secret-bearing provider credentials. Worker code must not initialize `memoryAgentLayer(storageRoot)` unchanged. Decide explicitly whether the model/provider client and tool runtime belong to the worker, and how they invoke central services without passing raw credentials.
2. Central server authenticates the request and resolves `sessionId → active Goal generation → immutable worker/code snapshot`. Client-supplied Goal IDs, ports, domain names and source paths are not authorities. Persist the binding and admission decision before dispatch, enforce a stable run ID and reject duplicate or stale admissions. A running turn remains bound to its old generation; a new Goal gets new code only when its snapshot is ready.
3. Define a versioned owner↔worker RPC for reads/writes, provider/tool calls, approvals and cancellation. Every mutating RPC needs an authorized session/run binding and idempotency or transaction boundary; a worker's failure cannot silently replay a tool or shell side effect. Keep migrations compatible with every live Goal generation, or block migration until old readers/writers finish; document rollback and backfill before a schema change.
4. Persist or otherwise recover the run/event cursor at the owner. On SSE disconnect, attach to the **same run** and replay only unseen events; do not start a second turn. On worker death, report an interrupted/unknown outcome until reconciliation; do not claim success or automatically rerun side effects. Preserve explicit cancellation and approval behavior. Stop old workers only after all their runs and dependent operations end.
5. Keep OAuth callback listening in the central owner (OpenAI's loopback port is fixed); an old-Goal worker must not close or recreate it. Test a pending login through a new Goal and callback after code changes.

## Current decision gate

The test-only IPC shape passes, but it is insufficient to claim the actual `AgentChat` can be split without changing its service boundaries. **Do not implement P03B or remove the existing build-ID 409 gate/storage lock on this evidence.** The next valid experiment must run an actual turn with the real service graph through an explicit owner/worker boundary (including an actual write, SSE reconnect, and crash/side-effect handling). If this boundary is too broad, keep the single owner and current gate and revisit the Goal-isolation requirement with the user. Portless or an internal domain can route to workers after that proof; neither substitutes for storage, authentication or run ownership.
