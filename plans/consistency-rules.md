# 기능 일관성 규칙 (토론 기록)

2026-11-21부터 사용자와 정한 규칙을 적는다. 겹치거나 모순되는 기능이 함께 따를 규칙 하나를 주제마다
정한다. 여기 적힌 규칙은 구현 계획(`plans/NNN-*.md`)의 근거이고, 구현할 때 그 계획이
`docs/decisions.md`에 항목을 더한다. 주제 번호는 `plans/README.md` "기능 중복 정리" 절의 군집 번호다.

## 정한 규칙

### R1. 승인자는 프로젝트 권한 모드 하나가 정한다 (2026-11-21, 군집 1·4)

- 규칙: 승인자가 누구인지는 프로젝트 권한 모드(`ask` 사용자 / `auto` 검토 모델 / `full` 없음) 하나가
  정한다. 무엇을 승인하는지(도구 호출, 실행 중에 더해진 카드, 처음 Plan)는 승인자를 바꾸지 않는다.
- 계기: 승인자를 정하는 손잡이가 둘이었다. 도구 호출과 새 카드는 권한 모드가, 처음 Plan은 입력창의
  Goal/Plan 모드(`WorkflowState.mode`)가 정했다. `ask` 프로젝트의 Goal 모드는 파일 쓰기 한 번은 묻고
  카드 스무 장짜리 Plan은 묻지 않고 시작했다.
- 따라 나오는 것:
  - 입력창의 Goal/Plan 모드를 없앤다(사용자 결정 "A로 하자"). 처음 Plan은 `ask`에서 카드 목록을 보이고
    "승인하고 실행"을 기다리며, `auto`·`full`에서는 사용자가 정렬 질문에 답한 run이 끝날 때 시작한다.
  - 2026-11-18 "Goal은 맞춘 뒤에 맡긴다"의 "무엇을 할지는 맞추고 어떻게 할지는 맡긴다"는 `auto`·`full`에서
    그대로다. 같은 결정의 버린 안 "Goal 모드도 Plan 승인 버튼을 누르게 하기"는 `ask`에 한해 바뀐다.
- 앞선 결정과의 관계: 2026-11-09 "Goal 모드는 … 계획자와 실행자가 나눠서 돈다"가 이미 "새 Plan 승인은
  프로젝트 권한 모드를 따른다"(`full` 바로 실행, `auto` 검토 모델이 Plan을 심사, `ask` 사용자 승인)고
  정했다. R1은 그 규칙을 처음 Plan과 Plan 모드까지 넓힌 것이다. `auto`의 Plan 심사가 지금 코드에 살아
  있는지는 구현 계획을 쓸 때 확인한다.
- 정렬 질문(2026-11-22): 정렬 질문은 모든 권한 모드에서 먼저 한다. Goal을 처음 저장하는 run은 Plan을
  만들지 않고 이해한 내용을 말한다. `ask`는 그 뒤에 만든 Plan을 보이고 "승인하고 실행"을 한 번 더
  기다린다. 버린 안: `ask`는 정렬 질문 없이 Plan까지 바로 만들고 승인만 기다리기. 지금 코드의 Plan 모드가
  그렇게 돌지만 원래 의도가 아니었다. 구현은 계획 031.
- 사용자: "프로젝트 권한모드 하나로 해야하는게 맞을듯.", "M1이 원래 의도였는데 … M1으로 고쳐줘."

### R2. 실행이 멈춰서 사람을 기다리는 것은 모두 판단 대기 함에 보인다 (2026-11-21, 군집 1)

- 규칙: 실행이 멈춰서 사람을 기다리는 것은 종류와 관계없이 판단 대기 함에 모두 보인다. 답은 함에서도,
  원래 자리(대화·보드)에서도 할 수 있다. 지금 열려 있는 대화의 것도 예외 없이 함에 보인다.
- 대상: 메인 대화의 도구 승인, 카드 에이전트·서브에이전트·외부 에이전트의 도구 승인(`RelayedApprovals`),
  새 카드 승인, 카드 판단(`HumanDecision`), 처음 Plan 승인(`ask`), 부작용 불확실 확인.
- 경계: "실행이 멈췄는가". 모델이 질문하고 턴을 끝낸 경우(예: Goal 정렬 질문)는 멈춘 실행이 없으므로
  함에 넣지 않는다.
- 계기: 함은 카드 판단과 카드 승인만 셌다(`decision-inbox.tsx:30`). 카드 에이전트의 도구 승인은 그
  대화 화면에만 떠서, 다른 프로젝트의 보드가 그것 때문에 멈춰도 함에서 알 수 없었다.
- 사용자: "어쨌든 그것도 같은 곳에서 승인받아야 하니까."

### R3. 같은 종류의 질문은 어디서 생겼든 같은 선택지와 같은 기록을 가진다 (2026-11-21, 군집 1)

- 규칙: 같은 종류의 질문은 어디서 생겼든 같은 선택지와 같은 기록을 가진다. 누가 물었는지(메인 대화,
  서브에이전트, 카드, 외부 에이전트)는 질문에 붙는 꼬리표다. 예외를 두지 않는다.
- 따라 나오는 것:
  - 도구 승인은 어디서든 "승인 / 거절" 둘이다(2026-11-23 사용자 결정 "A로 가자"). 처음에는 "승인 / 거절 /
    인자를 고쳐서 승인"으로 맞추려 했다. 계획을 쓰며 보니 인자를 고쳐서 승인하는 길(`editedArgs`)은 메인
    대화의 서버 코드(`loop/run.ts`, `chat-store/schema.ts`)에만 있고 화면은 어디서도 보내지 않았다. 그래서
    서버에서 그것을 지운다(계획 034). 인자를 바꾸고 싶으면 거절하고 모델에게 말로 고쳐 달라고 한다.
    버린 안(B): 화면에 인자 편집을 만들고 서브에이전트·카드·외부 에이전트의 승인에도 받게 넓히기.
  - 부작용 불확실 확인(`UncertainRuns`, `confirmUncertain`, `HumanDecision.UncertainSideEffect`)은 질문
    하나로 합친다.
  - 묻는 경로 셋(`tool_call` interrupt, `permission_review` interrupt, `RelayedApprovals`)을 "기다리는 것"
    계약 하나(종류 + 누가 물었는지)로 합친다.
- 순서: R2(함에 모두 보이기)를 먼저 하고, 경로 합치기를 그 뒤에 한다.
- 사용자: "ㅇㅋㅇㅋ."

### R4. Goal의 결과물이 되는 변경은 카드만 만든다 (2026-11-21, 군집 4)

- 규칙: Goal의 결과물이 되는 변경은 카드만 만든다. 계획자(보드가 도는 대화의 메인 채팅)가 직접 하는
  일은 결과물이 아닌 환경 일(git 상태, 패키지 설치, 판단을 위한 검사 실행)뿐이다.
- 계기: 보드가 도는 동안 코드를 고치는 손이 둘이었다. 카드 에이전트는 카드 worktree에 쓰고 검증을 받아
  Goal 브랜치에 들어간다. 계획자와 그 서브에이전트는 사용자의 메인 checkout에 쓰고, 검증이 없고, Goal
  브랜치에 들어가지 않는다. 2026-11-09 "계획자는 코드를 고치지 않는다"와 2026-11-13 "계획자도 plain
  chat과 같은 도구를 받는다, 쓰임은 모델에게 맡긴다"가 여기서 부딪혔다.
- 따라 나오는 것:
  - 도구는 2026-11-13 결정대로 둔다. 계획자가 rebase·설치를 못 하던 문제로 돌아가지 않는다.
  - 사용자가 실행 중에 시킨 작은 변경은 계획자가 직접 고치지 않고 카드로 보드에 더한다.
  - 계획자의 서브에이전트도 같은 규칙을 따른다.
- 강제(사용자 결정 "S2", 2026-11-21): 보드가 도는 동안 계획자와 그 서브에이전트의 `write_file`·
  `edit_file`·`delete_file`이 프로젝트의 추적 파일을 고치려 하면 서버가 거절하고, 거절 문구가 가벼운
  카드(R5)로 맡기라고 알린다. `run_command`는 그대로 둔다(rebase, 패키지 설치 같은 환경 일). 명령으로
  파일을 고치는 것까지는 막지 않는다. 가벼운 카드가 먼저 있어야 한다.
- 버린 안: 지침으로만 두기(2026-11-13의 한계 그대로), 막지 않고 보드 시작과 끝의 변경을 비교해 알리기
  (사용자가 고친 것과 구분하지 못하고, 일이 벌어진 뒤에 안다).
- 사용자: "그렇게 하자. 정책으로 할지는 좀 고민되긴 한데, 하위 에이전트를 좀 더 잘 쓸 수 있게 해야 하긴 할 듯."

### R5. 맡긴 일은 한 종류다 (2026-11-21, 군집 3)

- 규칙: 맡긴 일은 한 종류다. 맡길 때 세 가지를 정한다. 어디서 일하는가(부모와 같은 폴더 / 자기
  worktree), 누가 판정하는가(없음 / 검증자), 결과가 어디로 가는가(보고서만 / 브랜치에 통합).
- 따라 나오는 것:
  - 서브에이전트(같은 폴더, 판정 없음, 보고서만)와 카드(자기 worktree, 검증자, Goal 브랜치에 통합)는 같은
    것의 두 설정이다.
  - 없던 조합이 생긴다. 가벼운 카드(Plan을 고치지 않고 계획자가 도구 호출 한 번으로 맡기되 worktree에서
    일하고 Goal 브랜치에 통합한다. R4의 "작은 변경"이 이 길로 간다)와 격리된 서브에이전트(일반 대화에서도
    자기 worktree에서 일한다).
  - 기록은 맡긴 일 하나에 Work Trace 작업 하나다. 누가 띄웠는지(대화, 보드)는 문자열 접두사
    (`"kanban:"`)가 아니라 구조화된 데이터(tag가 있는 값)로 둔다. 사용자 조건: "종류 꼬리표가 구조화된
    데이터이면 괜찮다."
- 넓힌 범위(사용자): 프로젝트 폴더가 저장소 여러 개를 담은 workspace일 때 Goal을 돌리는 경우도 함께
  푼다. 아래 "토론 중" 참고.

### R6. 격리·브랜치·검증·통합의 단위는 저장소다 (2026-11-21, 군집 3·10)

- 규칙: 격리·브랜치·검증·통합의 단위는 프로젝트가 아니라 저장소다. 프로젝트는 저장소 여러 개를 담을
  수 있고, 맡긴 일은 자기가 쓰는 저장소를 밝힌다. 카드 하나는 저장소 하나에만 쓴다.
- 따라 나오는 것:
  - 카드에 "쓰는 저장소"(프로젝트 폴더 기준 경로, 비우면 프로젝트 폴더 자신)가 붙는다.
  - Goal은 손댄 저장소마다 Goal 브랜치를 하나씩 갖는다.
  - 카드의 작업 폴더는 프로젝트와 같은 배치다. 프로젝트 저장소의 worktree를 바닥에 두고, 그 카드가 쓰는
    저장소의 worktree를 원래 자리에 끼운다. Goal이 손댄 다른 저장소는 Goal 브랜치 상태로 들어 있고 읽기만
    한다.
  - 맞물린 변경은 저장소마다 카드를 두고 의존 관계로 잇는다. 독립된 변경은 의존 관계가 없는 카드들이라
    저장소별로 동시에 돈다.
  - Goal 전체 검증은 손댄 저장소들의 Goal 브랜치를 같은 배치로 한 폴더에 모아 놓고 한다.
- 버린 안: 카드 하나가 저장소 여러 개에 쓰기. 한 저장소는 통합되고 다른 저장소는 충돌한 반쯤 끝난 카드를
  다루는 규칙이 따로 필요해진다.
- 사용자: "X가 맞는 듯. 어차피 카드가 좀 더 늘어나는 게 린트 등의 혜택을 누리기에 더 편하다."
- 확인한 사실과 지금 동작은 아래 "토론 중"의 같은 제목 항목에 있다.

### R7. 여러 저장소에 걸친 Goal은 모든 저장소가 준비된 뒤에 한꺼번에 끝낸다 (2026-11-21, 군집 3·10)

- 규칙: 손댄 저장소 전부에서 사용자 브랜치를 Goal 브랜치에 합치고 충돌을 푼 뒤, 모아 놓은 폴더에서 Goal
  전체 검증을 통과시킨다. 그 뒤에 저장소마다 사용자 브랜치를 연달아 옮긴다(`advanceTarget`).
- 옮기는 사이에 어느 저장소의 사용자 브랜치가 움직였으면 그 저장소만 처음부터 다시 하고 나머지는 기다린다.
  저장소 사이에 원자성은 없지만 검증된 조합만 들어간다.
- PR로 끝낼 때도 같다. 저장소마다 PR 하나를 전부 준비된 뒤에 함께 열고, 본문에 같은 Goal의 다른 PR을 적는다.
- 버린 안: 저장소마다 준비되는 대로 옮기기. 맞물린 변경에서 한 저장소만 먼저 들어간 상태가 생긴다.
- 사용자: "P."
- 조언자가 정한 기본값(사용자가 바꿀 수 있다): 저장소 목록을 앱이 미리 찾지 않는다. 카드가 경로를 적고
  앱은 그 경로가 프로젝트 폴더 안의 git 저장소 최상위인지만 확인한다. 카드 작업 폴더의 의존성 설치는 그
  카드가 쓰는 저장소에만 한다.

### R8. 대화에 들어오는 메시지는 한 종류다 (2026-11-21, 군집 2)

- 규칙: 대화에 들어오는 메시지는 한 종류다. 보낸 쪽이 두 가지를 밝힌다. 누가 보냈는가(사용자 / 작업의
  끝 / 다른 대화 / 보드), 언제 전달하는가(답을 끊고 바로 / 쉬고 있으면 깨워서 / 다음 run에). 모두 같은
  곳에 저장되고 재시작해도 남는다.
- 따라 나오는 것:
  - 장부 넷(`queued_messages`, `work_tasks` 알림, `background_tasks.delivered_*`, `session_dispatches`와
    claim 표)과 메모리 상태 `kanbanAttention`을 세션 수신함 하나로 합친다. "누가 보냈는가"는 R5와 같은
    구조화된 값이다.
  - 보드의 호출도 DB에 남긴다(조언자가 정한 기본값).
  - 다른 대화가 보낸 메시지(`notify_session`)도 상대 대화를 깨울 수 있다(사용자 결정 "T1"). 깨우는 것의
    승인자는 R1대로 권한 모드가 정한다. `ask`는 판단 대기 함(R2)에 뜨고, `auto`는 검토 모델이 판단하고,
    `full`은 바로 깨운다. 보내는 쪽이 "다음 run에"를 고르면 지금처럼 승인 없이 남겨 둔다.
- 대체할 결정: 2026-11-13 "대상 세션의 다음 run에 전달한다"의 "세션에 대기 dispatch만 있으면 run을 자동으로
  기동하지 않는다". 2026-11-17 "작업의 끝은 띄운 쪽이 정한 방식으로 알린다"는 다른 대화의 메시지와 보드의
  호출까지 넓어진다.
- 버린 안: 다른 대화의 메시지는 늘 다음 run을 기다리게 두기.
- 2026-11-23에 사용자가 좁힌 것(계획 035가 실행한다):

### R10. 모델 선택은 계정까지 담고, 대화는 자기 선택을 지킨다 (2026-11-21, 군집 5)

### R12. 읽을 수 있는 스크립트만 예외를 받는다 (2026-11-22, 군집 7)

  승인하는 길은 두지 않는다.
- 계기: 스크립트를 지금은 글자로 읽는다(`shell/script-text.ts`). 그 읽기로 `auto`의 일상 명령 빠른 경로

- 샌드박스 안에서 실행할 때는 스크립트를 읽어서 정하는 것이 없다. 승인은 R1을 따른다.
- 예외는 넷이다.
  1. `auto`에서 검토 모델 건너뛰기
  2. 샌드박스 밖 실행
  3. "항상 허용" 규칙에 맞추기
  4. 스킬로 저장하기
- 예외 1~3의 기준 (한 번 실행할 글자):
  - 허용한 노드 종류만 있다. 연결은 `;`, 줄바꿈, `&&`, `||`, `|`뿐이다.
  - 낱말이 모두 글자 그대로다. 변수, 명령 치환, `"$@"`, 대입, redirect, heredoc이 없다.
  - 연결에서 쪼갠 명령이 하나도 빠짐없이 규칙에 맞는다(파이프의 양쪽도 각각, 선택 P1).
  - 읽지 못하면 거절한다(선택 A). 서버는 읽지 못한 부분을 모델에게 알려주고, 모델은 글자 그대로 다시 써서
    보낸다.
- 예외 4의 기준 (인자를 받는 프로그램):
  - 스킬이 실행하는 프로그램은 저장할 때 정해져 있어야 하고, 인자는 그 프로그램의 인자 자리만 채운다.
  - 변수, `case`, 함수, redirect, 명령 치환은 쓸 수 있다. 승인한 글자 그대로 실행되므로 사람이 읽은 것이다.
  - 값이 글자 그대로가 아닌 낱말은 명령 자리에 올 수 없고, "입력을 실행하는 명령"의 인자 자리에도 올 수 없다.

  - 받은 글자를 스크립트로 읽는 것: `sh`, `bash`, `eval`, `source`, `xargs`, 스크립트 인자가 없는
    `python`·`node`.
  - 다른 프로그램을 대신 실행하는 것: `timeout`, `env`, `npx`, `pnpm exec`, `ssh`, `find -exec` 등.

  - 이 목록의 명령은 "항상 허용" 규칙으로도 만들 수 없다.
- 한계: 목록은 완전할 수 없다. 목록에 없는 프로그램이 인자를 어떻게 읽는지는 앱이 모른다. 그 범위는
  샌드박스가 막는다. 변수가 든 스킬은 예외 2의 기준에 맞지 않으므로 샌드박스 밖으로 나가지 못한다.

### R16. 이미지 생성은 역할 하나이고, 이미지 모델도 다른 모델과 같은 길로 등록한다 (2026-11-22, 군집 9)

- 사용자(2026-11-22): 이미지 생성은 API 키를 입력해서 쓰는 것과 OpenAI 구독으로 쓰는 것이 모두 목적이다. 다른

    `imageGenerationEnabled` 스위치는 이 역할이 비었는지로 대신한다.
  - API 키 계정은 그 endpoint의 이미지 API를 직접 부른다. 키는 계정의 키체인 항목이다. 환경 변수

  - OpenAI 구독 계정에는 이미지 API가 없어서 모델 응답 안의 이미지 도구로 만든다. 이미지 버튼이 별도의 모델

### 저장소 여러 개를 담은 프로젝트에서 Goal 돌리기 (군집 3·10)

- 확인한 사실(2026-11-21, `/Users/creejee/work/opi-workspace`): 그 폴더 자체가 git 저장소이고(추적 파일

  `.gitignore`로 빠져 있다(`/web`, `/payment-bridge`, `/services/*`, `/sdk/*` …). submodule이 아니다.
- 지금 동작: 보드는 `git rev-parse --show-toplevel`로 저장소 하나를 찾아 Goal 브랜치와 카드 worktree를
  만든다(`kanban/git-worktrees.ts`, `orchestrator.ts:1438`). workspace에서는 그 저장소가 workspace 자신이라,
  카드 worktree에는 추적 파일만 있고 안쪽 저장소들은 없다. 카드가 실제 코드를 고칠 수 없다.
- 제안한 규칙: 격리·브랜치·검증·통합의 단위는 프로젝트가 아니라 저장소다. 프로젝트는 저장소 여러 개를
  담을 수 있고, 맡긴 일은 자기가 쓰는 저장소를 밝힌다.
- 사용자(2026-11-21): workspace의 Goal은 보통 저장소들이 맞물린 변경이고(예: 서비스의 API를 바꾸고 web이
  그것을 쓴다), 저장소마다 독립된 변경도 종종 있다. 작업 성격마다 다르다. 둘 다 돼야 한다.
